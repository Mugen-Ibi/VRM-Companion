# 追加デバッグ報告（2026-09-20）

対象: v0.0.0.4 / commit `29b326b`。入力系の前回指摘に加え、会話保存、キャンセル、モデル起動管理、VRM検査・登録、ファイル整理、SQLite復旧を確認した。製品コードは変更していない。

## 追加の指摘

### 1. 保存に失敗した会話がメモリ上の履歴に残る（P2、障害注入で再現）

`src/main/index.ts:138` の `message()` は、先に `c.messages.push()` してから `persist()` を呼ぶ。会話レコードの書き込みを失敗させると、sendはエラーになり、DBのメッセージ数は0だがメモリ上は1になった。再同期で未保存の発言が現れたり、その後の送信・保存に混入する原因になる。既報の「送信拒否で下書きが消える」と重なるため、両方を直す必要がある。

対策: 会話更新を複製上で組み立て、保存成功後にメモリと通知へ反映する。保存を無効にした場合のメモリ更新は明示的に分岐する。

### 2. 停止・失敗した応答の次の会話で、userが連続する（P2、条件付き再現）

`src/main/llama.ts:260` はエラーになったassistantメッセージだけを除外し、対応するuserメッセージを残す。`user → assistant(error) → user` の履歴を渡すと、テンプレート生成へのリクエストは `system → user → user` となった。

ロールの交互性を要求するテンプレートを模したサーバーではHTTP 400になり、失敗したターンを除いた対照条件は成功した。実モデルの種類によって許容が異なるため、すべてのモデルで発生するとは断定しない。

対策: 失敗したターンを単位として扱い、モデルへ渡す履歴に孤立したuserを残さない。再試行時に元の依頼を残す仕様なら、結合等の方法を明示する。

### 3. フォルダ選択中の停止後も、選択結果が確定する（P2、待機を挿入して再現）

`src/main/index.ts:674` のselectRootはtaskのAbortSignalを使わず、register完了後にrootIdを保存する。登録処理を待機させてcancelしたところ、最終phaseはcanceledだが、会話には新しいrootIdが設定された。

対策: registerへのキャンセル伝達と、許可・会話への関連付けを確定する直前の中断確認。単に画面を「停止」にするだけでは不十分。今回の再現はハンドラーと遅延した登録スタブによるもので、OSダイアログの手操作ではない。

### 4. VRM登録の保存失敗で、未登録のコピーが残る（P2、障害注入で再現）

`src/main/index.ts:979` の登録失敗処理はpreviewをnullにするが、インポート済みファイルを片付けない。タイマーも既に解除されている。avatarsレコードの保存を失敗させたところ、以前の選択は維持されたものの、登録されていないファイルが残り、後処理も予定されていなかった。失敗の反復でディスクを消費する。

対策: candidateを保持して未登録コピーの削除を試みる。削除できなかった場合に備え、起動時の孤立ファイル確認も検討する。元のユーザー提供ファイルは削除対象にしない。

### 5. 分割GGUFの2個目以降の変更を、再起動判定に含めない（P2、模擬プロセスで再現）

`src/main/model-runtime.ts:136` のsignatureは先頭ファイルのsize・mtimeだけを見る。2分割モデルを読み込み、2個目のサイズを変更して再度ensureしても、起動回数は1のままreadyを返した。

実際のllama-serverによるファイルロックの影響は未検証。後続ファイルを変更できる条件で、カタログ上のサイズと稼働中モデルが一致しなくなる。テストは独自の軽量HTTP子プロセスで、実GGUF推論は行っていない。

対策: 全分割ファイルのパス・サイズ・更新時刻をsignatureに含める。先頭以外の変更と、変更なしのキャッシュ再利用を両方テストする。

### 6. VRMの三角形数検査が、不正なaccessor.countで迂回される（P2、検査関数で再現）

`src/main/vrm.ts:51` はcountの型・非負整数性を検査せず加算する。countが900000と-900000の2プリミティブを含むGLBが検査を通った。これは壊れたモデルを入口で拒否できない問題。後続のGLTFLoaderが受理することや、実際に上限超過モデルが描画されることまでは確認していない。

対策: accessor参照、count、modeを検証し、有限・安全な非負整数のみで集計する。不正なJSONの型も、分かりやすい検査エラーとして拒否する。

## 対応順

1. 既報の下書き消失と、今回の保存失敗時のメモリ／DB不一致をまとめて修正。
2. 既報のAPIキー欄残留、失敗ターンの履歴組み立て、停止と確定処理の整合性。
3. VRM失敗時の後始末とメタデータ検証、分割モデルの再起動判定。

既存テストが通っていても、今回の境界条件が正しいことは保証されない。実Windows IME、透明ウィンドウの重なり、長時間常駐、実モデルのテンプレート差分は引き続き別途検証が必要。

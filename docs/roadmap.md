# VRM-Companion 開発・検証計画

作成・更新日: 2026-09-19 / 状態: 承認済み計画・実装後の受け入れ検証中

本書の完了条件と性能目標は維持する。最新の要件別結果・測定値・未実施項目は[検証記録](verification.md)を参照する。現在の実装や一部テストの成功をもって、P5や全必須要件の完了とは扱わない。

## 1. 開発順序

承認した開発順序は、表示・会話の基礎経路を確認し、整理・復元を加え、最後に常用可能性を実機検証する流れである。現在は表示・会話・整理・保存のコードを実装し、受け入れ検証と不具合修正を進めている。検証結果のない日付による納期は固定しない。

| 段階 | 実装・検証するもの | 完了条件／対応要件 | 更新時点の状況 |
| --- | --- | --- | --- |
| P0: 技術検証 | ユーザー提供VRM 1体の透明表示、クリック透過、llama-server接続、同時GPU負荷、Windows移動APIの小規模検証 | 採用構成、PC条件、モデル、互換バージョンを記録。透過とデータ保全の実現方式を確認 | Electron構成を採用し、実接続と実NTFSの基礎試験を実施。GPU共有・操作環境差の評価は継続 |
| P1: デスクトップ表示 | インポート、位置・倍率、表情・待機動作、トレイ、設定保存 | AV-01〜05、ST-02。LLMなしでも常駐可能 | コードとVRM／UIテストを実装。対応モデル・実機環境ごとの合否は検証記録で管理 |
| P2: 会話相手 | 日本語ストリーミング、人格、履歴、中断、接続障害 | CH-01〜04、ST-01の会話部分。UC-01/02を本人が試用 | 模擬サーバー試験と既存Qwen／llama-serverへの実接続を実施 |
| P3: 整理の提案 | Intent Router、対象引継ぎ、直下スキャン、固定分類、容量制限付き検証、プレビュー編集 | CH-05、AG-01〜03・08。提案だけではファイルを変更しない | コードと承認失効・ハッシュ中断等の回帰試験を実装 |
| P4: 整理の実行 | ハンドルベースの移動、ジャーナル、停止、再起動復旧、復元 | AG-04〜07。コピーした検証フォルダで異常系まで合格 | 実NTFS試験、保存故障注入、取消・復元競合を検証。手動照合終了と復旧・復元の読取り予算も実装 |
| P5: v0.1完成 | パッケージ化、2時間試用、オフライン検証、セットアップ説明 | 全必須要件を実機確認し、UC-01〜03を一通り実行 | 配布版と操作ガイドを作成し短時間試験成功。利用者の指定で2時間表示試験を後回しとして実装成果を引き渡す。全合格は未宣言 |
| P6: 日常性の改善 | 音声、リップシンク、記憶、再帰整理、意味による分類、定型作業の自動実行を優先順に追加 | 利用者の試用結果から次の1機能を選ぶ | MVP後の範囲として維持 |

P2は会話版として試用可能だが、プロジェクトの初期ゴール達成はP5とする。P0で実現性に問題があれば、透明入力方式、描画品質、フレームワークを比較し、設計書の判断を更新する。

MVPの最小の一連の体験は「ユーザー提供VRMとのテキスト会話 → 対象フォルダを選択 → 直下ファイルの種類別整理案 → 一括承認 → 移動・結果表示 → 復元」。P0は手元の1体から始めるが、P1/P5では異なるモデルとVRM両世代で特定モデルへの依存がないことを確認する。ユーザーの任意VRMという要件を、固定モデル専用へ縮小しない。

## 2. 検証する不確実性と実機条件

| 項目 | 実験 | 判断基準 |
| --- | --- | --- |
| 透明ウィンドウ | 透明部分・髪付近・ドラッグ・透過復帰・フォーカスを反復操作 | 背後のアプリ操作を妨げず、操作不能からトレイで戻れる |
| マルチモニター | 100/150/200% DPI、負座標、モニター切断、スリープ復帰 | 位置と当たり判定が一致し画面外に取り残されない |
| VRM互換性 | ユーザー提供の0.x/1.0、異なる作者・外見、表情不足、SpringBone、MToon、破損・巨大モデル | 対応モデルを表示・切替でき、表情不足でも会話・整理が動く。不正モデルは理由を表示 |
| LLM品質 | 日本語雑談、ユーザー設定の口調、整理依頼、未対応依頼、JSON形式、対象不足を含む固定20問 | 通常会話と整理を正しく分岐。未対応・曖昧な依頼で勝手に方式や対象を決めない |
| ハッシュ計算 | 512MiB/2GiB/200件の境界、上限超過、計算中キャンセル、計算前後のサイズ変更 | 超過時は対象を絞るまで開始せず、進捗を表示。不完全な検証で承認・移動しない |
| GPU競合 | 同じVRMで推論なし／推論あり、GPUオフロード量を比較 | UIが応答し、描画・生成速度の両方が実用域。VRAM不足時に回復できる |
| ファイル保全 | 親の差し替え、同名競合、使用中、強制終了を移動直前／直後に注入 | ルート外変更・上書き・二重実行が0件。状態不明時は停止 |

実接続の検証対象は、ユーザー提供の`Qwen3.5-9B-Q4_K_M.gguf`と既存llama.cpp b9843、`http://127.0.0.1:8080`である。公式b10964（0.4.1対応）を`.local/llama/b10964/`へ並置し、別の8081ポート・CPUで検証している。既存環境を更新・置換した扱いにはせず、新版のGPU互換性・速度・安定性を確認してから採用を判断する。アプリの既定8080は切り替えていない。

GGUFのファイル容量だけでVRAM使用量を見積もらず、描画分・KV cache分・余裕を含める。日本語応答・意図判定・構造化出力・速度・利用条件を確認し、llama.cppのビルドとchat templateを含めて採用構成を記録する。VRMモデルの探索・選定・入手はユーザーに委ねる。

確認済み実機はWindows 11 Pro、AMD Ryzen 7 260、RAM 32GB、RTX 5070 Laptop（VRAM 8GB）、NVIDIAドライバー32.0.16.1692。アプリはElectron 44.4.3、Three.js 0.180.0、three-vrm 3.5.5。アプリの既定contextは4096だが、個々の試験では実際のサーバー起動引数を記録する。ノートPCのAC接続・電源モードに加え、短時間の生成速度と継続使用時の発熱・ファン音・速度低下を本人が確認する。実機情報が判明したことだけでは最低スペックや速度を保証しない。

## 3. 性能計測の条件

CPU、GPU、VRAM、RAM、OS、ドライバー、Electron、Three.js、three-vrm、llama.cpp commit、モデルhash、量子化、context長、GPUオフロード設定を記録する。検証VRMのhash、三角形数、テクスチャ量、表示解像度も固定する。

描画は30秒のウォームアップ後、推論なし／ありで各5分測る。平均fpsとフレーム時間p95、UI応答p95、アプリ全プロセスのメモリ、VRAMを記録する。推論はモデル読込み済みの同じ10プロンプトで初回トークン時間と生成速度を測り、コールド起動時間は別記する。意図判定を先に行うため、ユーザーの送信から通常応答の最初の文字までの総時間も測る。NF-04の5秒目標はこの総時間に適用する。

NF-02〜05の目標を満たさない場合は、fps上限、影・物理・解像度、モデルサイズ、context長を順に調整する。実機情報のない段階で最低スペックや応答速度を保証しない。

## 4. 検証レベルと重要ケース

| レベル | 対象 | 必須ケース |
| --- | --- | --- |
| 単体 | パス方針、固定分類、計画、状態遷移、意図判定出力検証 | 未知の候補ID（Entry.id）、重複、相対逸脱、未知拡張子の保持、ルール版による再現性、上限超過、承認後編集、期限切れ |
| 通信結合 | llama-serverアダプターとIntent Router | SSE分割・中断、未準備、切断、不正JSON、構造化出力非対応、古いrequestIdの到着 |
| 会話・整理結合 | chat.sendからPlannerと結果表示まで | 対象未選択、別対象への言及、未対応方式、確認のキャンセル、権限解除、実行記録と定型報告の一致 |
| ファイル結合 | 実NTFS一時領域 + SQLite | サブフォルダ非走査、同名、Unicode、大小文字、長いパス、ロック、リンク、権限不足、容量不足、hash変更、バイト数境界とキャンセル |
| 故障注入 | 記録とファイル操作の境界 | 予定記録の前後、移動後・結果記録前に終了。再起動で元と先の状態を照合 |
| 復元 | 成功／一部成功の逆操作 | 元パス占有、移動先変更、権限解除、復元途中終了、復元の重複要求 |
| 実機UI | 表示、会話、設定、整理 | DPI、全体透過からの復帰、画面外位置、再起動、連続モデル切替、オフライン |

ファイルの検証には専用の使い捨てフィクスチャを使い、個人の実データをテスト対象にしない。権限境界は「正常系が動く」だけでなく、許可していない操作を拒否することで確認する。LLMが「完了しました」と誤出力したケースも、結果カードに成功として載らないことを確認する。

## 5. 配布と運用

初期はWindows向けのローカルビルドを本人が利用する。`scripts/build.mjs`でElectron／renderer／C#補助層をビルドし、`scripts/package.mjs`でWindows x64向けに梱包する。アプリ、VRM、LLMモデルを分け、READMEと操作ガイドに起動・接続・保存先・復元の説明を用意する。一般配布をする場合は、インストーラー、コード署名、更新方法、依存ライセンス表示を追加で設計する。

設定画面のDBバックアップと、起動失敗時のバックアップ復元導線を実装している。VRM本体・LLMモデル・整理対象はDBバックアップに含まれない。DB復元では元の破損ファイルを保持し、許可・承認を失効させる。保存時点以後の操作を自動再実行しない。詳細な配置と復元契約は[基本設計書](architecture.md)第7節を参照する。

キャラクター素材、モーション、音声、GGUFモデルは自動同梱しない。既存リポジトリのLICENSEは変更しない。アンインストール時に利用者の原本VRMや整理対象を削除せず、アプリデータ削除は明示的な別操作にする。

今回の引渡しでは、実装、配布版、操作ガイド、短時間の検証記録を提供する。2時間表示試験は利用者の指定で後回しとし、自動再開しない。後続では長時間試験、メモリ仮目標、実機操作の未実施ケースを要件ごとに更新する。手動照合終了と復旧・復元の読取り予算に対する回帰試験は完了した。性能目標の緩和や未実施項目の合格扱いによってP5を完了させない。

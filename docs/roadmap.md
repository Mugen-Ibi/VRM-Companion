# VRM-Companion 開発・検証計画

作成日: 2026-09-19 / 状態: レビュー反映版

## 1. 開発順序

初めに「表示と会話が気持ちよく使えるか」を確認し、その後にファイル整理を完成させる。技術検証の結果が出るまでは日付による納期を固定しない。

| 段階 | 実装・検証するもの | 完了条件／対応要件 |
| --- | --- | --- |
| P0: 技術検証 | ユーザー提供VRM 1体の透明表示、クリック透過、llama-server接続、同時GPU負荷、Windows移動APIの小規模検証 | 採用構成、PC条件、モデル、互換バージョンを記録。透過とデータ保全の実現方式を確認 |
| P1: デスクトップ表示 | インポート、位置・倍率、表情・待機動作、トレイ、設定保存 | AV-01〜05、ST-02。LLMなしでも常駐可能 |
| P2: 会話相手 | 日本語ストリーミング、人格、履歴、中断、接続障害 | CH-01〜04、ST-01の会話部分。UC-01/02を本人が試用 |
| P3: 整理の提案 | Intent Router、対象引継ぎ、直下スキャン、固定分類、容量制限付き検証、プレビュー編集 | CH-05、AG-01〜03・08。実ファイル変更はまだ公開しない |
| P4: 整理の実行 | ハンドルベースの移動、ジャーナル、停止、再起動復旧、復元 | AG-04〜07。コピーした検証フォルダで異常系まで合格 |
| P5: v0.1完成 | パッケージ化、2時間試用、オフライン検証、セットアップ説明 | 全必須要件を実機確認し、UC-01〜03を一通り実行 |
| P6: 日常性の改善 | 音声、リップシンク、記憶、再帰整理、意味による分類、定型作業の自動実行を優先順に追加 | 利用者の試用結果から次の1機能を選ぶ |

P2は会話版として試用可能だが、プロジェクトの初期ゴール達成はP5とする。P0で実現性に問題があれば、透明入力方式、描画品質、フレームワークを比較し、設計書の判断を更新する。

MVPの最小の一連の体験は「ユーザー提供VRMとのテキスト会話 → 対象フォルダを選択 → 直下ファイルの種類別整理案 → 一括承認 → 移動・結果表示 → 復元」。P0は手元の1体から始めるが、P1/P5では異なるモデルとVRM両世代で特定モデルへの依存がないことを確認する。ユーザーの任意VRMという要件を、固定モデル専用へ縮小しない。

## 2. 最初に検証する不確実性

| 項目 | 実験 | 判断基準 |
| --- | --- | --- |
| 透明ウィンドウ | 透明部分・髪付近・ドラッグ・透過復帰・フォーカスを反復操作 | 背後のアプリ操作を妨げず、操作不能からトレイで戻れる |
| マルチモニター | 100/150/200% DPI、負座標、モニター切断、スリープ復帰 | 位置と当たり判定が一致し画面外に取り残されない |
| VRM互換性 | ユーザー提供の0.x/1.0、異なる作者・外見、表情不足、SpringBone、MToon、破損・巨大モデル | 対応モデルを表示・切替でき、表情不足でも会話・整理が動く。不正モデルは理由を表示 |
| LLM品質 | 日本語雑談、ユーザー設定の口調、整理依頼、未対応依頼、JSON形式、対象不足を含む固定20問 | 通常会話と整理を正しく分岐。未対応・曖昧な依頼で勝手に方式や対象を決めない |
| ハッシュ計算 | 512MiB/2GiB/200件の境界、上限超過、計算中キャンセル、計算前後のサイズ変更 | 超過時は対象を絞るまで開始せず、進捗を表示。不完全な検証で承認・移動しない |
| GPU競合 | 同じVRMで推論なし／推論あり、GPUオフロード量を比較 | UIが応答し、描画・生成速度の両方が実用域。VRAM不足時に回復できる |
| ファイル保全 | 親の差し替え、同名競合、使用中、強制終了を移動直前／直後に注入 | ルート外変更・上書き・二重実行が0件。状態不明時は停止 |

LLMモデル名やサイズは未確定。対象GPUのVRAMから描画分・KV cache分・余裕を差し引いて候補を選ぶ。GGUFのファイル容量だけでVRAM使用量を見積もらない。日本語応答・意図判定・構造化出力・速度・利用条件を確認し、llama.cppのビルドとchat templateを含めて採用構成を固定する。VRMモデルの探索・選定・入手はユーザーに委ねる。

対象はWindows 11 Pro / RTX 5070 Laptop（VRAM 8GB）。初回検証は小型の量子化GGUFとcontext 4096を実験条件として開始し、品質とメモリを見て変更する。これは動作保証値ではない。ノートPCのAC接続・電源モードを記録し、短時間の生成速度に加えて継続使用時の発熱・ファン音・速度低下を本人が確認する。CPUとシステムRAMは測定開始時に記録する。

## 3. 性能計測の条件

CPU、GPU、VRAM、RAM、OS、ドライバー、Electron、Three.js、three-vrm、llama.cpp commit、モデルhash、量子化、context長、GPUオフロード設定を記録する。検証VRMのhash、三角形数、テクスチャ量、表示解像度も固定する。

描画は30秒のウォームアップ後、推論なし／ありで各5分測る。平均fpsとフレーム時間p95、UI応答p95、アプリ全プロセスのメモリ、VRAMを記録する。推論はモデル読込み済みの同じ10プロンプトで初回トークン時間と生成速度を測り、コールド起動時間は別記する。意図判定を先に行うため、ユーザーの送信から通常応答の最初の文字までの総時間も測る。NF-04の5秒目標はこの総時間に適用する。

NF-02〜05の目標を満たさない場合は、fps上限、影・物理・解像度、モデルサイズ、context長を順に調整する。実機情報のない段階で最低スペックや応答速度を保証しない。

## 4. 検証レベルと重要ケース

| レベル | 対象 | 必須ケース |
| --- | --- | --- |
| 単体 | パス方針、固定分類、計画、状態遷移、意図判定出力検証 | 未知のfileId、重複、相対逸脱、未知拡張子の保持、ルール版による再現性、上限超過、承認後編集、期限切れ |
| 通信結合 | llama-serverアダプターとIntent Router | SSE分割・中断、未準備、切断、不正JSON、構造化出力非対応、古いrequestIdの到着 |
| 会話・整理結合 | chat.sendからPlannerと結果表示まで | 対象未選択、別対象への言及、未対応方式、確認のキャンセル、権限解除、実行記録と定型報告の一致 |
| ファイル結合 | 実NTFS一時領域 + SQLite | サブフォルダ非走査、同名、Unicode、大小文字、長いパス、ロック、リンク、権限不足、容量不足、hash変更、バイト数境界とキャンセル |
| 故障注入 | 記録とファイル操作の境界 | 予定記録の前後、移動後・結果記録前に終了。再起動で元と先の状態を照合 |
| 復元 | 成功／一部成功の逆操作 | 元パス占有、移動先変更、権限解除、復元途中終了、復元の重複要求 |
| 実機UI | 表示、会話、設定、整理 | DPI、全体透過からの復帰、画面外位置、再起動、連続モデル切替、オフライン |

ファイルの検証には専用の使い捨てフィクスチャを使い、個人の実データをテスト対象にしない。権限境界は「正常系が動く」だけでなく、許可していない操作を拒否することで確認する。LLMが「完了しました」と誤出力したケースも、結果カードに成功として載らないことを確認する。

要件IDと検証結果をP5で一覧化し、未実施を合格と扱わない。現時点では設計資料のみであり、上記実機検証や性能測定は未実施。

## 5. 配布と運用

初期はWindows向けのローカルビルドを本人が利用する。アプリ、VRM、LLMモデルを分け、READMEに起動・接続・保存先・復元の説明を用意する。一般配布をする場合は、インストーラー、コード署名、更新方法、依存ライセンス表示を追加で設計する。

キャラクター素材、モーション、音声、GGUFモデルは自動同梱しない。既存リポジトリのLICENSEは変更しない。アンインストール時に利用者の原本VRMや整理対象を削除せず、アプリデータ削除は明示的な別操作にする。

| 確認項目 | 現時点の仮置き | 影響する決定 |

| 対象OS | Windows 11 Proを確認済み、x64を想定 | 透明表示、NTFS操作、配布形式 |

| 配布先 | 本人のみ | 署名、更新、サポート範囲 |

回答が得られるまでは上記仮定で設計できるが、モデルの採用と性能保証は対象PCでの測定後に決定する。次の実装着手点はP0の「VRM 1体の透明表示 + llama-serverの日本語応答」である。

# 入力操作の不具合調査（2026-09-20）

対象は配布版 v0.0.0.3。ユーザー報告は「起動後、直前に特別な操作をせず、入力欄をクリックしてもキャレットが出ず入力できない」。通常の起動だけでこの症状が継続する状況は、今回の隔離環境では再現しなかった。以下の再現済み不具合と、報告された症状の原因確定は区別する。

## 再現できた課題

### 1. エラー通知が入力欄のクリックを遮る（優先度 P1）

`src/renderer/styles.css` の `#toast` は画面下部に固定され、`z-index: 100`。長文時の高さ制限や入力欄と重ならない配置がない。`panel.ts` の `toast()` は通知を 6.5 秒間表示する。

配布版にモデル読み込み失敗を模した長いエラー通知を送ると、入力欄の中央のヒット対象が `message-input` から `toast` に変わった。入力欄以外にフォーカスを移してから、入力欄中央を座標クリックしキー入力しても、入力値は変わらず入力欄にフォーカスが入らなかった。通知が消えた後、同じ座標をクリックすると入力できた。

保存済みアバターの読み込み失敗は、起動時にもこの通知経路を使用する。ただし今回のユーザー環境でエラー通知が出ていた証拠はなく、報告の原因とは断定しない。通知がない状態で続く入力不能は、この条件だけでは説明できない。

対策は通知を入力欄に重ねない配置にすること。クリックを透過させるだけでは文字が見えない問題が残る。通知表示中の入力・送信・停止を座標クリックで検証する。

### 2. 状態更新で入力欄が作り直され、Undo 履歴が消える（P2）

`panel.ts` の `render()` は `app.innerHTML` 全体を置換する。フォーカスと選択位置を戻しても、ブラウザーが持つ編集履歴は戻らない。

`before` をキー入力 → 状態通知 → `-after` をキー入力 → Ctrl+Z を 2 回、という手順で、最初の Undo は `before` まで戻るが、2 回目でも `before` を消せない。入力欄の DOM オブジェクトが別物になったことも確認した。IME 変換中は再描画が保留されるが、確定直後に置換され、同様に Undo 履歴を失う。今回の CDP による変換確定では、確定文字自体の消失やその後の入力不能は再現しなかった。

対策は入力欄を通常の状態通知で破棄しない構造への変更。設定入力欄にも同じ全体再描画経路があるため、併せて対象にする。

### 3. IME の Enter 判定に不足がある（P2、イベント条件を再現）

送信判定は `key === 'Enter' && !shiftKey && !isComposing` のみ。`keyCode: 229`、`isComposing: false` の Enter を合成すると、入力欄が空になり送信処理に進む。`send()` 自体にも変換中の保護がない。

これはイベント条件を注入した再現であり、ユーザーの Windows IME が実際にそのイベント列を出したという証拠ではない。「クリックしてもキャレットが出ない」症状も説明しない。対策は IME 処理中のキーと変換状態を送信判定に含め、実際の Windows IME で確定 Enter と送信 Enter を検証すること。

## 再現しなかったケースと検証の限界

- 起動直後の入力欄クリックとキー入力：成功。
- 10 秒間待機した後の入力：成功。
- ウィンドウサイズ 820×600、1120×810 での入力：成功。入力欄は disabled / readOnly ではなく、通常時の中央ヒット対象は入力欄自身だった。
- 会話削除の確認をキャンセルした後、承認した後の入力：成功。ただし確認は Playwright のダイアログ API で処理した。
- CDP による日本語変換中の状態通知、変換確定、その後の入力：成功。Windows の実キーボードと IME の検証を代替しない。

Playwright の入力は対象の WebContents に送られるため、別のネイティブウィンドウがクリックを遮る問題を十分には検証できない。透明なアバターウィンドウは常に手前に置ける構成で、マウス透過を切り替える。この重なりと Windows のアクティブウィンドウ状態は、今回のユーザー報告について残る確認対象。DOM のフォーカス復元だけで修正完了と判断してはいけない。

## 次の対応

1. 通知の配置を修正し、通知中も入力欄をクリック・編集できるようにする。
2. 通常更新で入力 DOM を維持し、Undo・選択範囲・IME を回帰確認する。
3. IME の送信ガードを追加する。
4. 通知がないときの入力不能について、クリックの到達先、DOM フォーカス、パネルのアクティブ状態、アバターの重なりを同時記録して切り分ける。記録対象に入力本文や API キーを含めない。

調査時点では製品コードを変更していなかった。その後の改修依頼により、v0.0.0.4で通知配置、DOM維持、IME送信ガードを修正した。透明ウィンドウやOS側フォーカスが関わる未再現の症状については、引き続き原因未確定。

## 再現手段と証跡

`scripts/investigate-input.mjs` は専用の user-data-dir と固定診断文字列を使う。送信検証には専用のローカル HTTP モックを接続先として設定する。`COMPANION_PACKAGE` を省略するとビルド済み開発版を対象にする。終了コード 0 は診断の完走を示し、不具合がないことは意味しない。

```powershell
$env:COMPANION_PACKAGE = 'release/v0.0.0.3/VRM-Companion-win32-x64/VRM-Companion.exe'
node scripts/investigate-input.mjs
```

配布版での最終確認：

- `artifacts/input-investigation-1789878216024/report.json`
- `artifacts/input-investigation-1789878216024/startup-error-overlap.png`

これらはローカルの診断成果物であり、リポジトリの追跡対象外。

修正後の回帰判定には `node scripts/investigate-input.mjs --verify` を使用する。入力欄のDOM同一性、Undo、IME用Enterの非送信、通知表示中のクリックをアサートする。通常Enter・Shift+Enterと設定入力欄のUndoも確認する。開発ビルドでの成功証跡は `artifacts/input-investigation-1789878961788/report.json`。
